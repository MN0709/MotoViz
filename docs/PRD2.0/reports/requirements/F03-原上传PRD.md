## 1. 文档依据与使用方式

已明确要求来自 Issue #3、[接口契约](../api-contract.md)及[项目说明](../../README.md)。本地核对的代码基线为 `438b2b6`。

本文用“已明确”表示现有任务或接口已规定的要求；用“建议”表示为形成完整流程而补充的产品方案。建议项在评审通过前不视为团队已承诺的功能。本文不直接变更现有接口契约。

## 2. 背景与目标

改装店工作人员需要上传配件照片，为后续模型生成提供有效输入。系统应阻止不合规文件，修正图片拍摄方向，并让工作人员知道上传和预处理是否成功、失败后如何继续。

本模块交付到“可供后续模块使用的图片及上传记录”为止。模型生成效果、车型装配、3D 渲染由其他模块负责。

已明确的核心目标：

- 支持一次上传 1～4 张 JPG/PNG 图片，单张不超过 5MB。
- 4 张合计 20MB 的合规图片在验收环境中，3 秒内返回 uploadId。
- 非法格式全部拦截，并给出中文提示。
- 支持方向修正和预处理状态记录；中断后可重试，预处理失败保留原图。

## 3. 用户与场景

主要用户为改装店工作人员。典型场景是工作人员选择同一配件的若干角度照片，确认图片后上传；系统校验并处理图片，完成后把上传记录交给后续模型生成流程。

建议一批图片只描述同一个配件，页面提示“请上传同一配件的不同角度照片”；本期不使用 AI 自动判断图片是否属于同一配件。

## 4. 范围与边界

| 本期范围 | 本期不包含 |
| --- | --- |
| 选图、上传前预览与移除（建议） | 批量管理多个配件、历史图片库 |
| 数量、大小、格式校验 | HEIC、GIF、WebP 等其他格式 |
| 上传、中文错误反馈与手动重试 | 断点续传、分片上传 |
| 方向修正、保留原图、处理状态记录 | 自动抠图、AI 补图、背景生成 |
| 向模型生成模块交付上传记录 | 3D 模型生成与模型质量保证 |

压缩、缩放、输出分辨率不在现有 Issue 或接口中明确规定，须与模型生成负责人确认输入要求后决定，不能把任意压缩策略作为默认验收要求。

## 5. 主流程与页面内容

建议流程：进入配件上传区域 → 选择图片 → 本地校验 → 预览及移除 → 点击“上传图片” → 服务端校验并保留原图 → 创建上传记录 → 方向修正及状态更新 → 完成后允许进入模型生成。

建议页面包含：

- 上传说明：支持 JPG/PNG，1～4 张，每张不超过 5MB。
- “选择图片”入口、已选数量、每张图片的缩略图、文件名、移除按钮。
- “上传图片”按钮：无图片、存在校验错误或请求进行中时禁用。
- 上传 / 处理中的状态提示，以及错误后的“重试”或“重新选择图片”入口。
- 完成提示及后续流程入口；业务页面不要求用户手动复制 uploadId。

建议 MVP 使用文件选择器；拖拽上传和独立相机拍摄入口不作为必需交付。

## 6. 功能规则

| 编号 | 要求 | 依据 / 状态 |
| --- | --- | --- |
| U01 | 每批 1～4 张，只支持 JPEG/PNG；后端必须独立校验，不能只依赖前端 | 数量、格式已明确；校验分层为建议 |
| U02 | 每张最多 5MB；建议统一为 5 × 1024 × 1024 字节，界面与测试使用同一口径 | 5MB 已明确；字节口径待确认，当前 Mock 使用此值 |
| U03 | 服务端验证真实文件内容及可解码性，伪造扩展名或 MIME 的文件也须拦截 | “非法格式全部拦截”的建议实现要求 |
| U04 | 新选择后总数超过 4 张时拒绝本次新增，保留此前有效选择；其他无效图片在列表中标记，移除或替换后才可上传 | 建议 |
| U05 | 按图片方向信息修正输出；无方向信息时保持原方向；不自动猜测主体朝向 | 方向修正已明确；具体规则为建议 |
| U06 | 原图与处理结果分开保存，处理失败不得覆盖或删除已接收的原图 | 保留原图已明确；保存方式待技术评审 |
| U07 | 状态记录至少能够区分处理中、完成、失败，并关联 uploadId | 已明确；已有共享类型支持三种状态 |
| U08 | 原图保存失败时不得返回虚假的成功结果；预处理失败提示重试，不自动进入模型生成 | 建议 |
| U09 | 批次中任一图片校验失败则拒绝整批；任一图片预处理失败则批次标记失败，保留已保存原图及逐图处理结果 | 建议，批次策略待确认 |
| U10 | 正在上传时阻止重复提交；上传完成后修改选图应创建新批次，避免新旧 uploadId 混用 | 建议 |

原图至少须在约定的重试窗口内可用。保存位置、保存时长、清理机制、重启后是否恢复，由技术评审明确；当前 Mock 只在内存保存 ID，不能证明已满足原图保留要求。

## 7. 状态与异常

前端交互状态与服务端处理状态分开：选图、上传中属于前端状态；`processing / done / failed` 属于服务端状态，不向已有枚举中擅自添加值。

| 场景 | 页面表现（建议文案） | 后续行为 |
| --- | --- | --- |
| 未选图 | 请先选择至少 1 张图片 | 不提交 |
| 超过数量 | 一次最多上传 4 张图片 | 调整选择 |
| 格式不支持 | 仅支持 JPG 和 PNG 图片 | 移除或替换 |
| 单张超限 | 图片“文件名”超过 5MB，请更换图片 | 移除或替换 |
| 内容损坏或伪装格式 | 图片无法读取，请更换有效的 JPG 或 PNG 图片 | 服务端拒绝 |
| 上传中 | 图片上传中，请稍候 | 禁止重复提交；无法获得进度时不显示虚假百分比 |
| 网络中断 / 请求超时 | 上传未确认完成，请检查网络后重试 | 保留当前选择，允许重新提交 |
| 预处理中 | 上传已接收，图片处理中 | 等待最终状态，不提前进入生成 |
| 预处理失败 | 图片处理失败，原图已保留，请重试 | 仅在确实保存原图时显示此文案 |
| 完成 | 图片处理完成 | 交付 uploadId，允许后续操作 |

建议 MVP 采用用户手动重试，不做无限自动重试。网络中断后的整批重传不等于断点续传；若第一次请求已被服务端接收但响应丢失，可能生成重复记录，去重和幂等策略需技术确认。

对“已知 uploadId 的预处理失败”优先建议使用原图重试，无须再次上传；这需要补充服务端能力，当前契约尚未定义重试接口。

## 8. 接口与协作边界

沿用现有契约：`POST /api/3d/upload`，`multipart/form-data`，字段 `images`，成功返回 `201`，响应包含 `uploadId` 和 `status`。

沿用错误码：`IMAGES_REQUIRED`、`UNSUPPORTED_FILE_TYPE`、`UPLOAD_VALIDATION_ERROR`、`FILE_TOO_LARGE`。新增错误码或响应字段必须同步更新接口契约、共享类型、Mock 和调用方。

现有契约缺口及建议：

| 缺口 | 建议方案 | 决策影响 |
| --- | --- | --- |
| 返回 processing 后没有查询最终状态的约定 | 增加按 uploadId 查询状态的能力；具体路径与字段另行评审 | 前端能否获知完成、失败 |
| 未定义原图与处理结果如何供模型生成使用 | 服务内部通过 uploadId 查找原图 / 处理结果，不要求前端自行拼接路径 | 模型生成模块能否实际读取图片 |
| 未定义已上传图片的处理重试 | 提供按 uploadId 重试处理的能力 | 能否使用保留原图恢复 |
| 未定义 processing / failed 的 uploadId 能否生成模型 | 建议只允许 done 进入生成，其他状态明确提示 | 避免过早生成和错误输入 |

上述为方案建议，不是已存在的 API。若选择同步处理，也必须实测证明在目标环境满足 3 秒指标；不能仅为保持接口简单而忽略性能验收。

模块负责人负责上传与预处理流程；前端负责人确认页面接入位置；3D 组长与模型生成负责人确认存储、输出格式及交接方式。依赖 [Issue #1](https://github.com/MN0709/MotoViz/issues/1) 提供可运行的项目基础。

## 9. 验收用例

以下为验收设计，尚未执行，不代表测试通过。建议规则对应的用例在评审确认后纳入正式验收。

| 编号 | 输入 / 操作 | 预期结果 |
| --- | --- | --- |
| AT01 | 分别上传 1 张与 4 张有效图片 | 成功接收、返回 uploadId，可追踪最终状态 |
| AT02 | 不传图片、一次传 5 张、字段名错误 | 拒绝请求，中文提示符合契约 |
| AT03 | 单张大小恰好等于限制、超出 1 字节 | 边界内允许，超出时返回 413 |
| AT04 | GIF、HEIC、文本文件，含改扩展名 / 伪造 MIME 的样本 | 无一被当成有效 JPG/PNG 接收 |
| AT05 | 截断或损坏的 JPG/PNG | 中文错误提示，无虚假完成状态 |
| AT06 | 带不同 EXIF 方向的照片及无方向信息照片 | 输出方向正确，原文件内容保留 |
| AT07 | 上传中断后手动重试 | 页面可恢复，不重复触发后续模型生成 |
| AT08 | 模拟预处理失败 | 标记失败，原图可读取，可按确认方案重试 |
| AT09 | 混合有效 / 无效图片，或批次中一张处理失败 | 遵循确认后的批次策略，无含糊的“全部成功”提示 |
| AT10 | 4 张合计达到上限的有效图片 | 验收环境中 3 秒内收到含 uploadId 的响应 |
| AT11 | 返回 processing、done、failed | 页面分别显示正确状态，只有完成后进入生成 |

性能口径建议：从浏览器发起上传到收到完整 uploadId 响应计时，包含传输时间；首次返回不代表预处理已完成。用本地或约定局域网环境测试，记录设备、浏览器、网络上行、文件精确字节数、并发数以及冷启动 / 热启动条件，建议连续测 10 次并保留每次结果。该口径待评审确认，不能把本地结果表述为任意公网环境保证。

20MB 在 3 秒内传输对上行带宽有要求，应单独记录传输与服务端耗时。预处理最终完成时限尚未定义，评审时需补充，不可无限停留在 processing。
