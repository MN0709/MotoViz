# MotoFit AI RAG 技术路线可行性报告

> 日期：2026-09-12
>
> 范围：关键词检索 + OpenAI/豆包兼容 LLM HTTP API
>
> 不包含：本地向量库、Python 模型、真实维修准确率评测

## 1. 一句话结论

4 个 RAG API 的字段和最小链路可以交付，但当前证据只支持“小样本关键词检索可排序、Mock 结构链路稳定、非法 JSON 可降级、引用 ID 可受控映射”；真实 LLM 的结构成功率、P95 延迟和诊断合理率尚未验证，不能据此宣称 F12/F13 的生产指标已达标。

## 2. 验证实现

代码位于 `packages/rag-engine/src/feasibility/`，没有修改现有 RAG 功能入口。

- `keyword-search.ts`：轻量中文词元化、字段加权和 0-1 归一化。
- `llm-adapter.ts`：Mock/真实 HTTP 两种模式、JSON 约束、运行时校验、可信引用回填和降级。
- `validate.ts`：`FaultDiagnosisResult` 与 `KnowledgeEntry` 运行时结构校验。
- `sample-data.ts`：10 条配件、5 个知识片段。
- `demo.ts`：5 条配件查询、3 条诊断、非法 JSON、知识详情和反馈契约验证。

运行：

```bash
npm run feasibility --workspace=@motorcycle-ai/rag-engine
```

真实模式需要显式打开，避免无意消耗 API：

```bash
LLM_MODE=real \
LLM_BASE_URL=https://your-provider.example/v1 \
LLM_API_KEY=your-key \
LLM_MODEL=your-model \
npm run feasibility --workspace=@motorcycle-ai/rag-engine
```

## 3. 实测结果

### 3.1 配件检索

受控样例集共 10 条配件，5 条查询的预期 Top-1 命中为 5/5。

| 查询 | Top-1 | score | 预期命中 |
| --- | --- | ---: | --- |
| 川崎 Ninja 400 排气 | 碳纤维尾段排气 | 0.8875 | 是 |
| 本田 CBR500R R-11 | R-11 全段排气 | 0.9250 | 是 |
| KTM Duke 390 排气 | LV-10 尾段排气 | 0.8875 | 是 |
| Ninja 400 双泡风挡 | Racing 双泡风挡 | 0.9500 | 是 |
| CB500X SH36 边箱 | SH36 36L 边箱套装 | 0.9500 | 是 |

该结果不能替代 F12 的 50 条测试集 Top-5 指标。样本是为验证路线手工构造的，且第一条查询中，同车型但类别错误的风挡和减震仍得到 0.6375，说明仅靠词重叠会产生明显次级噪声。

## 4. 逐项结论

### a. `score` 能算出来吗？

能。当前方案对查询做 NFKC/小写归一化，按空格切词，并对连续中文补充二元词；每个查询词只取命中字段中的最高权重：名称 1.0、类型别名 0.9、适配车型 0.85、品牌 0.75、来源 0.45。权重和除以查询词数，天然归一化到 0-1。

实测 5 条手工查询 Top-1 为 5/5，证明该分数可以稳定计算和排序。但 `score` 只是文本相关性分，不是“配件兼容概率”，不能展示为准确率或适配置信度。车型和配件类型应先做结构化硬过滤，再在候选集内打分；还需建立最低分阈值，避免把弱相关结果补满 Top-N。

### b. LLM 能稳定输出 `FaultDiagnosisResult` 吗？

- Mock 模式：3/3 通过结构校验，格式链路可行。
- 非法 JSON：1/1 成功降级，返回 `degraded: true` 的内部结果，包装后的 API 结构仍合法。
- 真实模式（DeepSeek `deepseek-chat`，2026-09-12 实测 20 次）：**20/20 结构校验通过，0 降级**，结构成功率 100%。当前证据支持"deepseek-chat 在演示数据量下可稳定输出 FaultDiagnosisResult 结构"。

Prompt 要求只输出 JSON，并给出字段模板，是为了降低字段名、Markdown 和自然语言前后缀带来的结构漂移。但 `response_format: json_object` 最多保证 JSON 形态，不保证业务 Schema，所以代码仍按“解析 → 字段归一化 → 范围校验 → 引用校验”处理；任一环节失败就整体降级，不返回半份诊断。

`probability` 被约束为 0-1、两位小数，并明确为“当前资料支持下的相对置信度”，不是统计学故障发生率。未经过标注数据校准前，不应向门店用户展示成精确概率，建议前端先映射为高/中/低。

### c. `references` 能映射到文档吗？

能映射。真实适配器只允许模型返回 `knowledgeId`，随后由代码在本次传入的受信上下文中查找 ID，并用原始上下文回填 `title/excerpt/url/sourceType`。模型返回不存在的 ID 会触发整体降级，因此无法凭空伪造链接或原文。

当前契约仍有缺口：`possibleCauses[]` 没有自己的 `referenceIds`，只能证明“整个诊断响应有引用”，不能证明“每条原因分别由哪段证据支持”。若分级验收要求逐条结论可溯源，建议后续契约给 `PossibleCause` 和关键维修步骤增加 `referenceIds: string[]`，并逐项验证非空且属于召回上下文。

### d. 延迟是否能满足 F13 ≤5 秒？

本次没有真实 API Key，因此没有真实 LLM 延迟样本，不能验证“成功诊断 ≤5 秒”。Mock 的 0-0.02ms 没有外推价值。

**2026-09-12 补充实测（DeepSeek `deepseek-chat`，20 次循环，3 条症状轮流）**：延迟 P50=1.21s、P95=1.63s、P99=1.92s、最慢 1.92s。**P95 1.63s，显著低于 F13 ≤5 秒红线，余量充足**。样本为演示上下文（5 条知识片段），真实数据上下文更长后延迟会上升，仍建议 F13 开发期用真实数据复测。

适配器当前设置 4.5 秒超时，超时后返回结构化降级结果，这能保护接口不无限等待，但不等于真实成功调用能在 5 秒内完成。主要风险是供应商排队、跨网抖动、输入上下文过长、模型输出长度和重试。

在承诺 F13 前，应固定模型和区域，使用接近 Demo 的上下文长度至少跑 20-50 次，记录成功响应的 P50/P95、超时率、结构降级率；指标应以 P95 ≤5 秒衡量，而不是单次最快结果。可缓存“车型 + 归一化症状 + 知识版本”命中的常见诊断，但缓存不能跳过知识版本和引用有效性校验。

### e. 4 个 API 是否可交付？

| API | 结论 | 交付条件 / 风险 |
| --- | --- | --- |
| `POST /api/rag/search/parts` | 有条件可交付 | score 路线已跑通；必须增加车型/类型硬过滤、阈值和 50 条正式测试集 |
| `POST /api/rag/search/fault` | 有条件可交付 | Mock 和降级通过；真实模型结构率、诊断合理率及 P95 延迟未测 |
| `GET /api/rag/knowledge/{id}` | 可交付 | 格式验证通过；需保证 `knowledgeId` 与存储条目一一对应、删除后有失效状态 |
| `POST /api/rag/feedback` | 可交付 | 类型简单；正式实现仍需持久化、查询 ID 校验和重复提交策略 |

## 5. 建议优先级

1. P0：检索先按标准化车型与配件类型硬过滤，再做关键词排序；设置最低分阈值。
2. P0：真实 LLM 结构/延迟测试已用 DeepSeek 完成首轮（20 次，P95=1.63s，结构率 100%）；F13 开发期用真实数据复测，统计 P95、超时率和降级率。
3. P0：所有引用只接受召回上下文中的 `knowledgeId`，引用元数据由服务端回填。
4. P0：为 `possibleCauses` 增加逐条 `referenceIds`；否则“每条结论 100% 可溯源”无法由代码证明。
5. P1：概率先展示高/中/低；积累标注集后再做概率校准。
6. P1：缓存常见查询时把知识库版本纳入 key，避免返回旧引用。

## 6. 验证边界

- 样例中的 `example.com` 是本地可行性数据，不是已核验的真实维修来源。
- 5/5 是受控样例 Top-1，不等于 F12 的 Top-5 ≥80%。
- 3/3 是结构和引用 ID 验证，不等于 F13 的诊断合理率 ≥70%。
- 20 次真实 LLM 实测（DeepSeek）验证的是结构与延迟，**没有验证诊断内容的维修合理性**（合理率需有标注数据后评测）。
- 本报告 P95=1.63s 基于演示上下文长度，真实数据上下文更长时需复测。
