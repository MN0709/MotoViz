# F14 引用溯源交付说明

## 做了什么与原因

- 服务端回填引用标题、片段、来源链接和文档/页码/章节；不采信模型生成的元数据。
- 仍要求引用 ID 来自本次召回，并支持 `getCurrentDocuments` 实时快照；调用模型期间删除/变更的来源不能出现在正常或降级结果中。
- 配件检索通过可信知识条目 `parts[].partId` 关联证据，不根据名称猜测引用。没有证据时返回空引用。
- `ReferenceList` 提供可访问的展开按钮、片段、完整原文、原始链接和失效/重试提示。片段随检索响应返回，展开不等待详情请求。
- 页码和章节是可选采集元数据，不存在就显示“页码未提供”。测试用的第 12–13 页是合成 fixture，不是真实维修手册页码。

## 产物及接入

- shared 的 `SourceLocation`、引用元数据与配件结果扩展。
- rag-engine 的引用回填、配件证据关联与实时失效检查。
- Mock 配件目录知识详情和配件引用，保留故障详情原契约。
- 前端 `apps/web/src/components/ReferenceList.tsx`，F19 可以直接传入 `diagnosis.references` 或 `part.references ?? []`。生产环境需网关转发 `/api`；也可注入 `loader(id, signal)` 接入自己的 API 客户端。
- 联调页保留原首页，仅通过 `http://localhost:5173/?demo=references` 进入。先运行 `npm run dev:mock` 和 `npm run dev`。页面有故障、配件和不存在的 chunk 三类引用。
- `npm run test:rag`、`npm run test:mock`、`npm run test:references`；交互测试已纳入 CI。

## 项目影响与边界

将 AI 答案到原始资料的链路打通，防止伪造 ID、过期来源和模型编造引用元数据。引用存在性检查不等于自动证明诊断结论医学/机械上正确，仍需技师和检索质量评估。

这是基于 PR #23 的独立增量分支。#23 尚未合并，F14 PR 的基础分支先设为 `feat/F13-knowledge-diagnosis`；待 #23 合并后改向 main。

共享接口扩展需要 RAG/3D 两组确认。实时知识库服务需在集成时提供 `getCurrentDocuments`；未提供时仅检查传入的内存数据，不宣称跨进程删除已被处理。

Mock 和 demo 都是模拟数据，不代表供应商网页已核实或真实手册已标注。真实文档的位置元数据需 F09/F10 提供。

## 验收与下一步

- 自动验证可信元数据、伪造/删除/变更 ID、页码范围、危险链接、配件 ID 关联和降级不保留已删除来源。
- DOM 交互验证片段不等待 HTTP、404 失效、网络失败重试及空引用。其展开耗时不代表真实浏览器性能。
- 本机 Tabbit 因可执行文件缺失无法启动，真实浏览器点击到绘制的 200ms 指标及视觉验收尚未完成，不能把 F14 标记为全部验收通过。
- 下一步由组长确认接口扩展，F19 接入组件，知识库服务接入实时快照，补真实浏览器 200ms 与真实来源数据验收。
